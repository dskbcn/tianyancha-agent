# Spike 0.1: MCP client

Status: done, 2026-10-22. Plan item: `docs/plans/company-agent.md` 0.1.

Question: can a plain Node client talk to the 企业库查询 MCP server reliably, and what limits
must `packages/company-db` enforce?

## Decision: `@modelcontextprotocol/sdk` Streamable HTTP client, one per process, reconnect once

`Client` + `StreamableHTTPClientTransport` from `@modelcontextprotocol/sdk` 1.32.1, with
`requestInit: { headers: { 'X-API-Key': … } }`, works as is. It negotiates protocol
`2025-11-25`; the server reports `企业库查询` 4.1.3. No `mcp-remote` or stdio bridge is
needed.

The client keeps one connection and, when a call fails with a lost session, reconnects once and
retries the call. It never retries a call that the server answered with `isError`.

## Findings

1. **`query` returns at most 2,000 rows, and says `truncated: false` when it cut them.**
   `LIMIT 5000` and `LIMIT 20000` both returned 2,000 rows, `truncated: false`. The server
   flag cannot be trusted. `company-db` treats a full page (2,000 rows) as possibly truncated
   and pages with keyset or `OFFSET` when it needs more rows. `ORDER BY id LIMIT 3 OFFSET 2000`
   on 杭州 took 353 ms.
2. **A `SELECT` with no `LIMIT` and no `limit` argument can kill the session.** Before this
   spike, `SELECT id, company_name FROM tyc_advanced_search_companies` failed after ~8 s with
   HTTP/2 `INTERNAL_ERROR`, and the session was unusable afterwards. The `limit` argument alone
   is enough (`limit: 50` with no SQL `LIMIT`: 26 ms). `company-db` always sends `limit`, set
   to the 2,000-row page size or lower.
3. **A lost session fails with `-32600 Bad Request: Missing session ID`.** Reproduced by
   terminating our own session (`transport.terminateSession()`). A new `connect()` works at
   once. That error, and transport-level failures, trigger the one reconnect-and-retry.
4. **Rows are large.** `SELECT *` costs about 2.5 KB per row (2.5 MB for 1,000 rows), mostly
   `business_scope`. Three narrow columns cost about 100 bytes per row. This is why results go
   to disk and the model sees a preview.
5. **Full scans take 13–17 s.** Any aggregate over a filter on `city` / `established_date`
   reads the whole table (5.6M rows). Lookups by `id` or a join on `company_id` take 300 ms.
   Four concurrent scans ran in parallel (all ~17 s), so the server does not serialise calls.
   Tool timeouts: 120 s for `query`, 240 s for `find_companies`.
6. **`find_companies` is slow but takes a big page.** 54 s for 杭州 AI companies since
   2025-10-22 (37,284 keyword hits + 1,024 semantic-only, `limit: 20`). 40 s for 杭州 charging
   companies in 2026 with `limit: 5000, min_score: 0.5`: 3,074 rows, 828 KB, `next_offset:
   null`. One call with a large `limit` beats paging, since every page re-runs the search.
   `score_distribution` gives the counts at 0.40–0.60, which is what the model needs to choose
   a cut-off.
7. **`semantic_search` is fast** (1.2 s, top 5). Embeddings are `Qwen/Qwen3-Embedding-8B`,
   cosine; no reranker configured (`reranked: false`). It returns `company_id` and `score`
   only; the join back to names took 307 ms.
8. **Errors are tool results, not protocol errors.** An unknown column returns `isError` with
   the Postgres message; a `DELETE` returns `isError` with `SQL 校验未通过 … 只允许 SELECT`. The
   session survives both. The message is Chinese and specific, so `company-db` passes it to the
   model unchanged for a retry.

## Consequences for the plan

- `QUERY_ROW_CAP` is a total across pages; one page is 2,000 rows.
- Every `query` call carries the `limit` argument.
- `company_find` makes one call with `limit = FIND_ROW_CAP`, and pages only when
  `next_offset` is set.
- Tool progress matters in the web UI: typical answers wait 15–60 s per call.
