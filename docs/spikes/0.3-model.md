# Spike 0.3: model

Status: done, 2026-10-22. Plan item: `docs/plans/company-agent.md` 0.3.

Question: which Bailian model should the agent default to, and can it write correct SQL for
this data with a free `query` tool, or does it need structured tools?

## Decision: `deepseek-v4.1-flash-1017` by default, free SQL stays

Candidates (owner's choice): `deepseek-v4-pro-0813` and `deepseek-v4.1-flash-1017`, through
`@ai-sdk/openai-compatible` 3.0.75 (`ai` 7.0.137) at
`${ALIYUN_BAILIAN_API_HOST}/compatible-mode/v1`. Tool calling works with both, with no
provider options.

| | `deepseek-v4.1-flash-1017` | `deepseek-v4-pro-0813` |
|---|---|---|
| Golden set | 15/15 | 15/15 |
| Median / max time per question | 18.9 s / 34.5 s | 21.5 s / 48.2 s |
| SQL calls (15 questions) | 17, no errors | 15, no errors |
| Tokens in / out (15 questions) | 35,358 / 5,446 | 38,273 / 8,153 |

Both are correct on every question, so accuracy does not decide. Flash is faster, uses fewer
output tokens, and its answers carry more of the caveats the skill asks for. A structured
`company_stats` tool is not needed: with the pitfalls in the prompt, every SQL statement was
valid on the first try.

`ALIYUN_BAILIAN_MODEL` switches models at runtime, so pro remains a configuration change
away. Revisit when the golden set grows harder questions (2.3). This set is at the ceiling for
both models.

## Setup

- One tool, `company_sql`: one `SELECT` through MCP `query` with `limit: 200`; returns
  `columns`, `row_count`, `rows`, or `error` with the server's message.
- The prompt is a draft of the skill: compact data dictionary, coverage per city, the
  pitfalls from spike 0.2, and "end with `最终答案：…`".
- An answer passes when every expected value appears in it (thousands separators and
  `YYYY年M月D日` dates normalised). Expected values come from direct SQL run the same day.
- SQL calls from both models shared a pool of 3 concurrent calls (finding 1).

## Findings

1. **The server has a statement timeout, and concurrent scans can hit it.** Computing the
   truth with 15 concurrent scans failed with `canceling statement due to statement timeout`.
   `company-db` allows at most 3 concurrent `query` calls per process
   (`COMPANY_DB_CONCURRENCY`, default 3).
2. **`ORDER BY id LIMIT n` with a selective filter times out by itself.** `WHERE city=… AND
   established_date='2026-09-15' AND … ORDER BY id LIMIT 1` timed out; without `ORDER BY` it
   took 13 s. Postgres walks the primary-key index and filters row by row. The skill says not
   to sort by `id` with filters, and paging in `company-db` sorts by `id` only for narrow
   follow-up reads (by `id` ranges), not for filtered scans.
3. **Both models handled the coverage trap.** Asked for 深圳 "最近一个月", both said the data
   ends on 2026-05-20, counted the month before that date, and split out 个体工商户.
4. **Flash volunteered useful caveats.** For q05 it reported that 59.5% of the rows had no
   registered capital. For q02 it found 2 rows with a null `enterprise_type`, which
   `enterprise_type <> '个体工商户'` silently drops. That is the behaviour the skill should ask
   for, and a `NULL` note joins the pitfalls list.
5. **Contact columns appear unasked.** For q14 (look up by credit code) flash selected
   `legal_representative` without being asked. This confirms that contact fields are
   stripped in `company-db`, on the rows, not left to the prompt.
6. **Time is mostly the database.** One scan is 13–18 s of a 17–35 s answer. More model speed
   barely helps; fewer scans per answer does. The skill's "one query with `COUNT(*) FILTER`"
   rule did that: 32 of 32 tool calls were single statements.
