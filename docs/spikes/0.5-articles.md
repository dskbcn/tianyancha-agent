# Spike 0.5: 公众号文章 (upstream addition)

Status: done, 2026-10-22. Plan item: `docs/plans/company-agent.md` 1.8.

The 企业库查询 MCP server (still reporting version 4.1.3) added three tools and two tables on
2026-10-22: WeChat articles about companies settling in 杭州. Question: what is in them, how do
they relate to the company table, and what must the agent know to use them correctly?

## What the server added

| Tool | Use | Measured |
| --- | --- | --- |
| `search_articles` | Semantic + keyword search; filters: settle types, districts, date range, `company_id`, accounts | 150–400 ms, ~0.7 KB per hit |
| `get_article` | Metadata + body, paged by `offset` / `next_offset` | 30 ms; typical body ~1.6k chars |
| `article_facets` | Totals and the valid filter values | 50 ms |

Tables: `wechat_articles` (one row per article) and `wechat_article_chunks` (embedded text chunks,
used by search). `wechat_articles.company_id` = `tyc_advanced_search_companies.id`.

## Findings

1. **Small, single-source library.** 467 articles, all from one account (湖畔自留田), published
   2025-02-21 → 2026-10-20. Answers must say so: this is one outlet's coverage, not a register of
   every settlement.
2. **Settle types.** 总部迁入 147, 项目落地 121, 新成立 110, 新设子公司 83, 研发中心 5,
   新设团队/业务单元 1. Labels come from an LLM at ingest (`llm_reason` says why) and can be wrong:
   in the live test, 「杭州AI安全公司，总部悄然搬到了北京」 is tagged 总部迁入.
3. **Joins cleanly to companies.** 384 of 467 articles carry a `company_id`, and all 384 match a
   company row (46 ms with the primary key). Industry, capital, status and establishment date of
   the companies in the news come from the company table.
4. **Bodies are not in SQL.** `query` accepts `wechat_articles` with these columns only: `id,
   title, account_name, publish_date, url, settle_type, district, origin_city, company_name,
   company_id, credit_code, llm_reason, read_count, like_count, share_count, comment_count,
   created_at, updated_at`. `content_text` / `content_md` are rejected; read bodies with
   `get_article`.
5. **`district` is unreliable.** 71 null; non-district values (未来科技城, 杭州市); 深圳 districts
   (南山区 ×5, 龙岗区) on articles about companies moving *to* 杭州 (it records the origin). For
   district statistics prefer the joined company's `district_county`.
6. **Other columns.** `origin_city` is mostly null and inconsistent (北京 / 北京市). `read_count`
   caps at 100001 ("10万+"). `publish_date` is a real DATE (unlike the company table's TEXT dates).
7. **SQL over articles is fast** (25–150 ms; the table is tiny), so counting and grouping articles
   goes through `query`, as the server's instructions also say.

## Consequences

- Tools `article_search` and `article_read` (in `packages/company-db` and `apps/agent`); counting
  and lists stay in `company_sql`. `article_facets` is not wrapped: `GROUP BY` gives the same.
- Skill `company-news`: coverage, tool choice, the SQL column whitelist, the join, the data traps
  above, and how to cite (title, date, link; "据报道" for claims not checked against the register).
- Search results are saved as a result file, so artifacts can use them as `DATA`.
- Live checks (DeepSeek V4.1 Flash): "2026 年总部迁入杭州的企业，行业和注册资本分布" answered with
  joins only (98 articles → 55 companies) and flagged the mislabelled 北京 article; "机器人企业来杭州
  设研发中心或总部" used search → read → `company_profile`, and the registered legal representative
  and district matched the article.
